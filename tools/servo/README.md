# Jetson 双电机范围标定与状态监视

在 Jetson 的 `/home/nvidia/jetson_mech_control` 使用本工具。当前对象是
伺服电机 104、105。程序使用已部署的 `Ak30ServoSystem`、session 和共享
`BusRuntime`，不另写串口协议。框架源码、构建与安装目录保留在
`servo-current` 指向的持久版本中。

双板通信隔离排查使用独立的[有界双板诊断工具](dual_board/README.md)。
该工具默认仅输出计划；真实收发要求电机 CAN 物理断开，离线测试不代表板端通信验收。

单板只写一次初始化后接收全部 CAN ID，以及三项电机隔离资格验证，使用[接收观察与隔离台架工具](observer/README.md)；它不保证 listen-only，也不证明电机已接收命令。

电机断电断 CAN 后，对固定 mode6 命令与合成反馈同时收发的隔离对照，使用[单进程双板双向诊断](duplex/README.md)；默认只打印计划，采集完整性与固定内容及数量匹配分别判定。

## 第一次使用

```bash
cd /home/nvidia/jetson_mech_control
./servo-status check
./servo-status
```

`check` 只检查配置与实际框架解析，不打开设备。正常监视需通信板及电机
已接通，串口使用稳定的设备路径。没有设备、端口被其他程序占用或反馈
失效时，程序报告原因；不会改用另一个串口，也不会把缺失反馈显示为零。

屏幕显示每台电机的设备角度、电气转速 ERPM、电流 Iq（A）、板温（°C）、
原始状态和反馈新鲜度。ERPM 不是输出轴 RPM 或机构角速度，Iq 不是力矩。
按 Ctrl+C 退出。可用 `./servo-status --duration 10` 观察十秒。

## 手动标定

先退出已有监视或控制程序，确认机构适合手动摆动，再运行：

```bash
./servo-range
```

1. 按屏幕提示手动摆到右端，停稳后按回车，记录两台电机成对位置。
2. 手动摆到左端，停稳后按回车，再次记录。
3. 查看结果并按提示确认保存。默认在每台电机观测范围的两端各内缩
   **10°设备反馈角度**。可通过 `--margin-deg` 明确修改。

工具同时记录摆动过程中的角度极值。任一电机没有有效新鲜反馈、仍在
运动、出现故障，或内缩后没有有效区间，都不能保存该次标定。
中途取消不会覆盖已有标定。首次部署没有虚构的运动范围，必须先标定。

配置保存在根目录 `config/servo_pair.json`，与软件版本目录分开保存。
保存时保留先前配置备份及本次端点、极值、余量、映射与时间记录。
标定不会设置设备原点、写入电机 Flash 或驱动电机运动。

## 让控制框架使用范围

```bash
./servo-control
```

此入口根据已保存配置生成 URDF，再交给实际 ROS 硬件插件；每台电机的
`position_min_rad`、`position_max_rad` 都取自本次标定。未标定时拒绝启动。
轨迹控制器 `servo_trajectory_controller` 默认保持 **inactive**，不会因启动
自动执行轨迹。关节名为 `motor104_joint`、`motor105_joint`。
限位在下一次启动生效，不在运行中的控制循环内热修改。
标定结束时机构仍在机械端点，位于内缩后的软件范围之外；启动控制前先
手动移回两台电机均处于软件范围内的位置。可先用 `./servo-status` 查看，
退出监视后再启动控制。`./servo-control check` 可先离线检查运动配置。

这些限位约束每台电机的数值范围；左右端点的成对记录并不能证明区间内
任意两角度组合都适合耦合机构。设备零点、接线身份或坐标映射改变后应
重新标定。断电前后若角度基准改变，不沿用旧记录。

一次只运行一个伺服入口。监视/标定为独占只读会话，不能在控制程序占用
同一串口时再打开；占用时会拒绝启动。旧位置、速度、轨迹入口属于以前
的力控部署，不读取此伺服标定文件，不能与新入口同时运行。

## 开发验证

Python 用合成反馈验证标定、失效状态和配置消费；C++ FakeSerial 测试验证
真实插件读取及零电机发送。完整验证由仓库 `tools/ci/build_workspace.sh`
执行。离线测试通过不等于已采集现场端点；实际端点由操作者手动标定。

## 双电机位置试验：servo-move

在部署目录运行 `./servo-move`。这个入口使用相同的标定配置和现有框架：
`FollowJointTrajectory → servo_trajectory_controller → Ak30ServoSystem → session / BusRuntime`。
它自行启动独立命名空间中的控制进程，控制器初始 inactive；不要同时运行
`servo-control`、独立 `servo-status` 或其他电机程序。运行期间直接在本窗口查看反馈。

操作顺序：

1. 先把机构放在标定后内缩范围以内。运行 `./servo-move check` 可只检查配置，
   不启动 ROS、不打开串口；运行 `./servo-move` 后等待“控制器已就绪”（两个控制器加载完成且有双机反馈）。
2. 输入 `enable`，确认使能后保持当前位置。启动工具不会自动使能轨迹控制器。
3. 输入 `move <104目标角度> <105目标角度> <移动秒数>`。
   两个角度都是设备绝对角度（度），与标定/监视使用同一套设备坐标，不是相对增量；
   工具不修改零点。按配置中各电机自己的映射换算，并拒绝超出保存限位的目标。
   时间范围为 0.5～60 秒。请根据当前读数选小幅目标，先单机变化、再双机组合；
   单个电机限位不保证任意双电机组合都适合机构。
4. 移动时显示目标、实际角度和位置差分得到的**估算速度**。当前 ROS 伺服状态仅有
   position；电流、温度、原始故障码明确显示“未发布”，速度不冒充 ERPM 或独立速度测量。
   控制器反馈状态与原始设备故障码不同；硬件插件仍执行现有反馈及限位检查。
5. 等待轨迹完成后继续输入下一组目标。运动期间新 `move` 被拒绝，避免排队或意外替换。
   使用起点/终点零速度的插值轨迹；指定时间是主机轨迹时间，实际响应还受驱动参数及机械负载影响。
   action 以 0.5°设备目标角度对应的关节容差、额外 3 秒等待检查到达；超时或失败结束本次操作。
6. `stop` 取消旧轨迹，再请求保持当前测量位置，电机仍可输出力矩。
   `disable` 和 `quit` 都尝试保持并停用控制器，确认本工具启动的框架进程组退出后，
   通过正式协议/USB传输发送每台电机的模式15（DLC0），逐台等待状态0x77确认。
   `disable` 保留交互会话，停止后台，拒绝 `move`/`step`；界面只显示上次测量，当前角度和速度未知。
   再输入 `enable` 才启动新的 inactive 框架，等待新的双机反馈及硬件健康检查，再使能并接管当前测量位置。
   `quit` 失能并退出；已成功 `disable` 后直接 `quit` 不重复发送失能命令。
   Ctrl-C、终端输入结束和程序异常也尝试这个退出流程；控制器停用失败仍会在框架退出后尝试失能。
   框架退出未确认时不抢占串口；任一写入或确认失败都明确报错，不能显示失能成功。
   失能或清理未确认时结束本次操作，禁止在此会话重新使能；失能确认失败不会自动重发并覆盖失败日志。
   **失能确认不等于机械静止或制动；反馈中断、断线或无法确认时请现场断电。**
   硬件故障时跳过保持请求，不新增运动目标。强制杀进程/掉电无法保证软件清理执行。

记录保存在部署目录的 `runs/servo/move-*`：

- `config.json`、`control.urdf`：本次使用的配置与实际启动描述，原标定文件不改动。
- `events.jsonl`：成对目标、位置反馈、估算速度、action 结果、启停及异常时间。
- `disable.log`、`disable-trace.jsonl`：逐台失能确认、实际模式15帧及系统写入；与运动链记录分开。
- `framework.log`：本次框架日志。启动后20秒反馈或控制器仍未就绪会退出并提示检查日志。

首次后台的记录保留以上目录布局；再次 `enable` 的完整记录分别保存在
`backend-002/`、`backend-003/` 等目录，包括配置、URDF、事件、框架、命令链、原始串口和失能记录。
根目录 `events.jsonl` 保留整个交互会话的时间线，`backend` 字段关联各后台；
各后续目录的事件保存同一真实输入时间，便于命令链审计。失能期间没有后台或新鲜反馈记录。

这些记录可用于对照你观察或测量的机构姿态；工具不替代输出姿态测量或运动学模型。
突然断电或强制杀死进程不属于正常退出清理保证。

### 增量移动

在同一 `servo-move` 窗口中，`move` 仍表示绝对角度；新增：

```text
step <104增量角度> <105增量角度> <移动秒数>
```

例如 `step 5 -3 3`：从本次读取的实际位置出发，104 增加 5°、105 减少 3°，
移动时间为 3 秒。某台不需要改变时填 `0`。每次重新以有效的实际反馈为起点，
不累加到上一次指令目标；正负方向沿用设备角度坐标。

需要先 `enable`；有运动未完成、反馈过期、输入无效或换算后的绝对目标超限时拒绝。
窗口仍显示换算后的绝对目标；日志额外记录本次起点、增量和最终目标。

### 硬件故障与到达超时的区分

控制器显示 active、ROS 位置消息持续更新，不等于硬件仍正常。工具会在使能及发送
目标前查询实际硬件组件状态、两台 position 命令接口的可用性；运行中每 0.2 秒发起
异步检查（1 秒响应期限）。硬件失效后不再接受 move/step，也不再根据缓存位置
发送保持目标，转为关闭本工具的框架进程；后续旧位置消息不能恢复该会话。

`events.jsonl` 的 `hardware` 记录包含组件生命周期、接口可用/占用状态。
`framework.log` 记录伺服运行时首次故障，帮助区分反馈、发送、目标包络与时限问题。
过去运行未记录的首因不能凭后续 action 超时反推；不要用增加容差或等待时间掩盖
硬件失效。接口检查是操作层诊断，不代替实时硬件层保护，也不证明物理断能。

`servo-move` 保存 `serial-trace.jsonl.gz`：记录宿主串口实际读写的原始字节、
调用起止时间及返回值。单条最多1024字节，原长度和捕获长度分别保存；
较早记录可能被环形缓存覆盖，文件头明确给出数量。
TX成功仅证明宿主串口调用成功，不证明网关已上总线或电机已执行。
该记录用于排查保持目标、发送间隔与原始反馈，不能替代真实CAN抓包。

### 全链路诊断（SERVO-001）

`servo-move` 自动启用 `command-chain.jsonl.gz`，与 `events.jsonl`、
`serial-trace.jsonl.gz`、`framework.log`、`capture-manifest.json` 及本次配置
一起保存在运行目录。首个后台直接使用 `move-*` 目录，再次使能使用其中的
`backend-002` 等子目录；整次窗口会话共享同一磁盘额度。
独立启动插件仍可用旧的 `MECH_SERVO_CHAIN_PATH` / `MECH_SERVO_TRACE_PATH`
保存原 JSONL；该兼容入口仍使用旧缓存，并不具有新的持久磁盘额度管理。

记录使用同机单调时间、控制周期、joint 索引、命令代数和串口调用编号关联：

- 操作输入、切换请求及确认、轨迹请求；操作事件里的反馈仅是客户端观测，
  保持初值以 `claim_before/claim_after` 的实际接口值为准。
- `interface`：上游控制器实际共享命令单元；`dispatch`：授权与刷新标记；
  `stored`：运行时接收的目标与软截止时间。
- `prepared/submitted/selected`：会话编码、队列提交与发送前选中的实际 CAN 帧；
  `transport_send/result`：USB 编码器入口和真实返回结果。
- `serial_request/result`：完整 USB 报文；`syscall_write`：每次系统调用开始/结束时间、
  请求数量、实际接受字节、返回值及 errno。短写和 EINTR 分别记录，不能把请求全包
  当成系统已经接受全包。初始化包也经过相同记录。
- 原始反馈帧、接管前后测量、首故障、取消及运行时停止。

离线核对（不打开设备）：

```bash
python3 tools/servo/chain_audit.py /absolute/run/path/command-chain.jsonl.gz
```

审计器独立解码、校验 USB CRC，核对目标映射、CAN 选择、USB 载荷和实际写入字节，
报告各层首个不一致及发送间隔。`complete=true` 只表示捕获到的主机链路一致，
不证明通信板 CAN 送达、电机接受或模式6使用语义正确。任何缺层、截断、丢记录、
写入错误或未完成调用都会使审计失败；没有系统写入的 FakeSerial 日志也不能通过。

全速记录写入启动前准备的 `/dev/shm/servo-trace-*` tmpfs 二进制快照，
控制循环不格式化日志、不写持久磁盘。链缓存默认4194304条（保留开始部分），
原始串口缓存524288条（保留最后部分），合计约1396 MiB RAM，最大1536 MiB。
`--chain-capacity` / `--raw-capacity` 可以调整条数；设置较小容量会缩短完整捕获窗口。
目标是支持约五分钟双机500 Hz实验，但最终是否完整必须检查实际 `dropped`、
`overwritten`、`closed` 及 manifest，不能只根据运行时间判断。长时间未使能也会消耗容量。

启动前检查 RAM、tmpfs和持久磁盘空间：RAM额外保留256 MiB，磁盘保留1 GiB；
整个 `move-*` 会话最多128 MiB，整个 `runs/servo`（含已有文件）最多2 GiB。
不足时在启动设备后台前拒绝；已有证据不会自动删除。链压缩文件最多96 MiB、
原始串口压缩文件最多16 MiB，单份操作事件最多2 MiB、框架输出最多4 MiB，
另保留关闭和元数据空间。再次使能继续计入原会话额度。框架输出超过额度仍持续读取，
避免堵塞后台；操作事件的丢弃和日志错误会明确写入 manifest。

确认原框架进程组退出并执行正式模式15失能步骤后，才开始流式gzip导出。
不产生巨大的未压缩中间文件，也不通过插件析构写出完整JSONL。导出期间窗口显示等待提示，
不开放再次使能。日志失败不跳过失能步骤，也不增加任何自动电机运行超时。
`servo-move` 的专用启动器关闭 ROS launch 文件日志，所有ROS节点关闭外部文件日志，
屏幕输出汇入有界 `framework.log`，避免在 `~/.ros/log` 留下重复的无限增长记录。

导出失败会保存 manifest并保留自己的tmpfs快照，禁止新建另一个大快照。
进程崩溃遗留的同用户、同日志根目录快照也会在下次启动时阻止分配。
先确认原程序已结束，按提示目录离线恢复（无设备访问）：

```bash
python3 tools/servo/trace_storage.py --snapshot-dir /dev/shm/servo-trace-XXXX \
  --run-dir /absolute/runs/servo/move-XXXX/backend-002 \
  --session-root /absolute/runs/servo/move-XXXX
```

恢复器检查原写入进程组已消失，拒绝读取仍在写入的快照；失败输出和既有日志保留，
重试产生独立的 `*.recovered-*.jsonl.gz` 文件，manifest给出实际文件名。
若额度不足，需要先手工归档先前压缩输出，再重试。成功保存全部可读证据及明确结果后，
只删除该次自己创建的tmpfs目录；未正常关闭或记录丢失仍会标记不完整，审计不能通过。
崩溃时未关闭的原始串口满环缓存可能有一个正在改写的槽，恢复时保守略过该槽。
tmpfs掉电后消失，不能承诺掉电恢复。审计器虽流式解压，当前仍保存关联表，
长记录的离线审计RAM使用随记录数量增长。监控不改变控制参数、限位、看门狗或停止策略。

## 105 单机试验

`./servo-move check --motor-id 105` 离线检查完整的 `config/servo_pair.json`，
再确认 105 选择；不启动 ROS、不打开设备、不修改配置。
`./servo-move --motor-id 105` 使用正式框架，仅生成 105 的硬件关节、轨迹控制器
关节和失能目标；启动必须收到 105 的真实新鲜反馈。此模式暂只接受 ID 105，
省略选项时保持原 104/105 双机格式与行为。

单机窗口显示 105 的限位、目标和实际角度。输入 `move 105目标角度 秒数`
或 `step 105增量角度 秒数`，例如 `move 20 3`、`step 1 2`；角度映射、
标定限位、反馈新鲜度和硬件状态保护均沿用原框架。

单机没有按运行时长自动失能或退出的上限。轨迹完成后保持目标；
`disable` 尝试保持并停用控制器，确认后台退出后向105发送模式15并等待失能确认，
随后保留窗口。`quit` 执行同样失能流程后退出；成功`disable`后直接`quit`
不会重复失能发送。再次`enable`新建后台，以新鲜实测接管。
反馈、硬件状态、目标限位及框架的命令有效期保护仍然有效；故障或失能未确认会报错。

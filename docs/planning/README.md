# Jetson 通用机电控制框架总体规划

> 规划基线：2026-07-28
> CubeMars 资料复核：2026-08-03
> 适用范围：NVIDIA Jetson、最多 6 台电机、2 条 CAN/CAN FD 总线、2 台 HI12、1 个未来 STM32 传感器节点
> 当前状态：FND-000～FND-004 已完成；下一步是在 FND-005 前执行 FND-004A Jetson ARM64 原生烟测；未启用 CAN、未控制设备、未修改 Jetson

## 结论标记

- **已确认事实**：来自本地手册、2026-07-28 的 Jetson 只读检查、项目明确要求或可信官方资料。
- **有依据的推断**：基于已确认事实形成的工程建议；实施后仍须用测试验收。
- **待确认项**：缺少决定性证据；必须同时给出确认方法、负责人和最迟时间。

**已确认事实**：本目录中的所有结论按上述三类标记。表格中的“性质”列适用于该行全部内容；一个段落前的标记适用于该段落，直到出现下一标记。

**正式决策边界（2026-08-07）**：[FND-004 ADR 索引](../adr/README.md)是 ADR-001/002/003/004/005/006/009 的当前规范入口；其中 ADR-006 保持 Proposed，表示当前单 `can0` 部署尚未获得实机配置和总线证据。规划正文继续提供背景、证据和路线，若与正式 ADR 冲突，以 ADR 状态和内容为准。

## 1. 执行摘要

**已确认事实**：当前验证机是 Jetson Orin NX 开发套件，运行 Ubuntu 22.04.5、L4T 36.4.7、ROS 2 Humble；已安装 ros2_control，但只有一个处于 DOWN/STOPPED 状态的 `can0`，没有 `can1`、`ros2_socketcan` 或 `ros2_canopen`。当前内核只能确认 `PREEMPT`，不能确认 `PREEMPT_RT`。[E01][E02]

**用户确认事实 + 资料事实**：当前两台定制电机均基于 AKE60-8，定制内容包含结构重新设计和 CubeMars 双编码器；结构不属于本软件任务。最新且明确覆盖 AKE60-8 的 AK3.0 V3.2 手册说明 servo 与力控/MIT-like 命令都使用扩展帧，并称同一代固件使用时无需模式切换；但两个命令族的 ID、payload 和接口语义仍不同。两台实机的固件、配置、双编码器 CAN 来源、定制参数和命令超时行为尚未读取。[L07]

**资料事实**：V3.2 给出标准 AKE60-8 的 Kt `0.7382 N*m/A`、`-15..15 N*m` 候选范围和输出端扭矩公式，状态帧 `0x29` 可配置 `1–2000 Hz`。这些值足以建立可配置 codec 和测试向量，但不能在未核对定制实机参数前硬编码。[L07]

**已确认事实**：HI12 标准 CAN 交付通常是 J1939、29 位扩展帧、500 kbit/s、默认节点地址 8。CANopen 是特定交付固件，不是 J1939 固件的普通运行时选项。若两台设备仍为默认地址，它们会冲突。[L03][L04]

**Accepted ADR**：长期架构采用“纯 C++ 传输/协议/时间/状态核心 + 薄 ros2_control 适配层”；每条物理 CAN 总线在控制进程内只有一个协调运行时。规范边界见 [ADR-001](../adr/ADR-001-core-boundary.md)、[ADR-002](../adr/ADR-002-bus-runtime-ownership.md) 和 [ADR-003](../adr/ADR-003-composite-system-interface.md)。

**用户提供（待独立确认）**：当前两台 AKE60 定制电机与两台 HI12 计划共用 Jetson 的 `can0`，暂时没有第二路接口。[ADR-006](../adr/ADR-006-conditional-can0-deployment.md) 因缺少共同位速率、节点/ID、终端和实测负载证据保持 Proposed；框架保留最多两条物理总线，不能仅为共总线而盲改未知设备配置。

**规划决定（2026-08-03 复核）**：当前两电机正常 MVP 的 `controller_manager` 与电机命令/反馈目标仍为 500 Hz，HI12 初始 100 Hz，Python 策略 20~50 Hz。V3.2 的 2000 Hz 是反馈配置上限，不是控制循环验收值。100~200 Hz 只作为模拟/首次硬件 bring-up 的保守档，代码和配置需支持 1 kHz 控制循环测试；1 kHz 电机通信是否启用由单 `can0` 负载和时序实测决定。可选 `0x2A` 会增加一帧位置反馈，必须单独计入预算。详见 `05` 和 `06`。

**规划决定（2026-08-03）**：当前立即进入无真实硬件依赖的 `Foundation v0.1`。先由项目负责人统一建立 Git、构建/CI、纯 C++ core、fake/vcan、BusRuntime、模拟设备、薄 `SystemInterface` 和模拟 demo controller；实机资料不再阻塞基础框架，只阻塞真实设备 profile 激活和物理验收。当前详细执行入口为 `07_framework_bootstrap_plan.md`。

**已确认事实（2026-08-07）**：FND-002/FND-003 的 pinned dependency manifest、五包 ROS 2 骨架、共享 build/test 脚本和最小 GitHub Actions/context workflow 已完成并推送；`Ubuntu-22.04` 中官方 `rosdep` 与显式 `ROSDEP_COMMAND=rosdepc` 两条路径均完成 5 包构建和 30/30 测试，GitHub Actions 的 context check 与 pinned Humble Docker build 也成功。具体提交与 run 证据由 Git/GitHub Checks 保存；该证据不覆盖 ARM64、vcan、性能或硬件结论。

**规划决定（2026-08-07）**：FND-004 完成后、FND-005 开始前增加 `FND-004A`。该任务在目标 Jetson Orin 的 ARM64 原生 Ubuntu 22.04/ROS 2 Humble 环境，从 clean clone 执行 context check、依赖解析和五包 build/test，并记录 JetPack/L4T/ROS/GCC/CMake；不启用 CAN、不操作真实设备、不代替 FND-015 的性能、sanitizer、稳定性和 RC 验收。

**治理决定（2026-08-07）**：`memory/` 改为每位开发者本地恢复工具并由 Git 忽略；根 `AGENTS.md` 继续强制使用 `project-memory` 和事件触发的 `write-codex-handoff`。长期事实进入 ADR/正式文档，共享任务状态进入 GitHub Issues/Milestones，README 不记录频繁变化的 commit/run ID。

**已确认事实**：按经典 CAN 最坏位填充估算，8 字节标准帧为 135 bit，8 字节扩展帧为 160 bit，均包含 3 bit 帧间隔。六台电机每周期一发一收、均按 8 字节扩展帧保守计，在 1 Mbit/s、200 Hz 时占 38.4%，250 Hz 时占 48.0%，500 Hz 时占 96.0%。因此 500 Hz 不能作为六电机通用默认值。

**Accepted ADR（2026-08-07）**：[ADR-009](../adr/ADR-009-effort-semantic-gate.md) 要求恒定命令 demo 只验证控制链路；只有供应商/配置证据证明协议字段、方向、减速比和机械侧映射确实支持输出端 N·m 时，真实 profile 才可暴露标准 `effort`。若只确认 Iq，则使用明确的电流接口。物理输出精度与最小框架 demo 分开验收。

**有依据的推断**：一个月内完成软件骨架和最小恒定命令 demo 具有可执行性；真实硬件部分还取决于四个不可绕过的实施闸门：设备身份确认、被动抓包通过、电机只读反馈通过、机械/电气台架通过，之后另有 G4 集成发布闸门。demo 通过只证明框架命令链路贯通，不等于最终控制算法完成，也不等于物理输出力矩精度通过。

## 2. 明确推荐

| 决策 | 推荐 | 性质 | 关键理由 |
|---|---|---|---|
| 核心边界 | 纯 C++ 核心 + ros2_control 薄适配 | 有依据的推断 | 协议可脱离 ROS 测试；总线所有权统一；更换 ROS/Jetson 的影响集中在适配层 |
| CAN 所有权 | 每条物理总线一个进程内 `BusRuntime` | 有依据的推断 | 多 socket 不会“抢帧”，但多个独立写者会破坏调度、超时和故障归因 |
| ros2_control 组件 | MVP 使用一个配置驱动的复合 `SystemInterface` | 有依据的推断 | 同时拥有电机、IMU 和总线，避免多个插件争夺同一总线；未来按证据再拆分 |
| 电机协议 | 每台设备配置期固定 active command profile | 有依据的推断 | AK V3.2 servo 与力控命令族虽可同固件存在，但 ID/payload/claim 不同；激活期间禁止自动猜测或混发 |
| HI12 协议 | 先识别交付固件，再选 J1939 解析器或 CANopen 栈 | 已确认事实 | 帧类型不能替代固件身份确认 |
| MVP 拓扑 | 候选单 `can0`，框架保留双总线 | ADR-006 Proposed | 共总线需同位速率、无 ID 冲突和负载/仲裁实测；未转为 Accepted 前不激活，新 Jetson 到位后再评估拆分 |
| 当前两电机频率 | 控制/电机目标 500 Hz，IMU 100 Hz | 规划决定 | 两电机带宽预算允许；500 Hz/1 kHz 都必须在 Jetson 和真实总线上量化验证 |
| 时间基准 | 主机单调时钟管新鲜度；设备采样时刻单独保存 | 有依据的推断 | 到达时间不等于采样时间；墙钟调整不得破坏超时判断 |
| Python 边界 | 独立非 RT 进程，以序号、有效期、边界和模型版本交付目标 | 有依据的推断 | DDS/GPU 抖动不能进入电机更新路径；过期命令必须在 C++ 侧失效 |
| 部署 | 目标运行原生，开发/CI 可使用容器 | 有依据的推断 | 原生便于设备、调度与权限控制；容器保留依赖复现价值 |
| 数据 | Git 只保存代码、配置和清单；大数据进 NAS/对象存储 | 有依据的推断 | 当前磁盘已约 80%；rosbag、日志和模型不应污染 Git 历史 |

## 3. MVP 范围与非目标

**已确认事实**：MVP 必须覆盖两台 HI12、至少一台基于 AKE60-8 的定制电机、可用电机反馈、受限台架最小恒定命令链路 demo、ros2_control 硬件骨架、至少一个 C++ 控制器、受控切换、诊断/超时/限幅/记录/复现。[L01] 该 demo 是框架验证项，不是最终控制目标。

**有依据的推断**：MVP 的软件范围包括纯 C++ 编解码与总线核心、vcan 模拟、复合硬件接口、一个有界 effort 测试控制器、状态广播、诊断、实验清单和部署脚本设计。真实设备操作只在后续实施阶段且通过闸门后执行。

**已确认事实**：本轮非目标包括实现真实设备驱动、启用 `can0`、安装或升级 Jetson 软件、修改内核/网络/服务、开发 STM32 固件、设计 STM32 模拟前端、实现神经网络控制、设计机械与电气安全系统。[L01]

**有依据的推断**：首月还不做多发行版维护、微服务化、云平台、数据库、复杂前端、自动固件升级、在线 servo/MIT 切换、六电机真实系统集成或安全认证。

## 7. 成功定义

**有依据的推断**：本规划成功不是“所有未知参数都被猜出”，而是团队能够直接据此建 Issue，知道哪些事实可用、哪些决策已经做出、哪些闸门不可绕过，并能在月末用记录、计量和故障注入客观判断 MVP 是否通过。

**待确认项**：真实设备参数、第二 CAN 接口、台架安全与力矩计量、实际调度抖动和真实总线错误行为只有在后续实施阶段才能确认；确认方法、负责人和截止时间已列入执行计划。

## 1. 审查结论

**用户确认事实**：当前两台定制电机的基础机型已经从“仅知 AKE60 系列”收敛为 **AKE60-8**。供应商资料库把标准目录项写作 `AKE60-8 KV80`，但不能仅凭目录名进一步断言定制实机仍使用标准 KV、绕组、减速器参数、驱动板固件或控制参数。

**资料事实**：AK3.0 V3.2.0 手册明确列出 AKE60-8，并覆盖 AK3.0 的 servo、力控/MIT-like 扩展帧协议、状态反馈、CubeMarsTool 配置与参数导出。

**用户确认事实（2026-08-19）**：`company/ak-series-driver-manual-v1-0-18-for-ak-2-0-robotic-actuator-cn.pdf` 中记录的 CAN 协议和 CAN 参数与当前两台电机一致。因此，L02 不再在本项目中被简单标记为“仅 legacy 参考”：它是当前电机协议的首要实现依据，包含两条需要分别实现和验证的 profile——伺服模式 29 位扩展帧，以及运控/MIT 模式 11 位标准帧。该确认仍不等于已经读取每台电机的固件、ID、实际 active profile、编码器来源或机械参数。

**规划决定**：现有资料足以开始离线设计和单元测试 `AK V1.0.18 servo-extended` 与 `AK V1.0.18 motion-control/MIT-standard` 两个 codec；先实现扩展帧 profile，再实现标准帧 profile。两者共享 canonical state/command 和 session 边界，但不共享会混淆帧类型、ID 或位域的打包函数。实机接入前仍须取得每台电机的只读配置、固件版本、active profile 和双编码器 CAN 字段来源。

### 4.2 双编码器

**资料事实**：AK V3.2 第 7 页把内环编码器写为 `21 bit` 单圈绝对值；双编码器型号的外环编码器为可选 `15 bit` 单圈绝对值。AKA V3.0 提供了相同的内/外环命名，可作为 CubeMars 双编码器通用旁证。

**资料事实**：AK V3.2 的 UART 参数响应同时包含“电机外环位置值”“编码器角度”和“外编码器角度”，说明固件数据模型能够区分外环位置与两个编码器相关字段。

**证据边界**：当前手册没有明确说明 CAN `0x29` 或可选 `0x2A` 的位置到底来自内环编码器、外环编码器还是固件融合值，也没有证明 CAN 能同时直接上传两个编码器值。因此不能先行决定 `joint/position` 的来源，更不能把两编码器角差直接解释为力矩。

**资料矛盾（2026-08-23 深读发现）**：L02 V1.0.18 第 7~9 页产品规格表写编码器为 **14-bit 单圈绝对值**，与 AK V3.2 双编码器资料的 21-bit 内环 / 可选 15-bit 外环不一致。两份手册描述的可能是不同代硬件；定制双编码器实机以哪套规格为准必须逐台确认（已列入 [05 §5.1](05_decisions_and_open_questions.md) 供应商问题清单第 3 条）。另注意 L02 第 31 页：原点设置命令 `Data[0]=1`（设置永久零点）**仅限双编码器机型**；单/双编码器机型对该命令的行为差异未在手册中说明。

### 4.3 CubeMarsTool 与实机配置

AK V3.2 第 15–17 页说明 CubeMarsTool 可以：

- 读取和写入电机、编码器参数；
- 配置 CAN 周期回报/问答模式、CAN 位速率、反馈速率和 CAN ID；
- 导出 `.AppParams` 与 `.McParams` 参数文件。

**规划决定**：首次实机核对只执行连接、版本读取、参数读取、截图和导出，不执行“电机参数识别”“编码器参数识别”“写入参数”“恢复默认”或固件升级。识别流程会驱动电机旋转，不属于只读证据获取。

### 4.4 L02 V1.0.18 CAN 命令族（当前实现基线）

#### 4.4.1 伺服模式：29 位扩展帧（第一实现目标）

L02 第 27~40 页规定伺服命令使用 29 位扩展帧：扩展 ID 的 bits[28:8] 为控制模式（功能 ID），bits[7:0] 为电机 ID。命令族（功能 ID）：0 占空比、1 电流环、2 电流刹车、3 转速、4 位置、5 设置原点、6 位置速度环；数据均为大端。关键缩放（2026-08-23 深读，第 28~32 页）：电流 `int32/1000` [A]（±60 A 编码范围）、位置 `int32/10000` [°]（±36000°）、位置速度环 8 字节 = 位置 int32/10000 + 速度 int16/10 + 加速度 int16/10。

反馈（第 32~33 页，人工复核）：**定时上传模式，上传频率可配置 1~500 Hz**；`0x29` 为 8 字节实时状态：位置 `int16/10` [°]（±3200°）、速度 `int16×10` 电气转速、电流 `int16/100` [A]、驱动板温度 `int8`（-20~127 ℃）、报错代码 `uint8`。故障码表（第 33 页）：0 无故障、1 电机过温、2 过流、3 过压、4 欠压、5 编码器故障、6 MOS 管过温、7 电机堵转。

**codec 必须处理的附加帧**（此前未记录）：功能 ID `0x09` 表示电机处于跳转引导状态；`0x2C` 为电机进入伺服模式的起始帧，回复固定 `0xFA 0xFB 0xFC 0xFD`。注意 `0x29` 反馈位置（int16，±3200°）与位置命令（int32，±36000°）分辨率/量程不对称。命令和反馈的 ID、DLC、字节序、缩放与错误码必须形成 golden/negative vectors。

#### 4.4.2 运控/MIT 模式：11 位标准帧（第二实现目标）

L02 第 41~45 页规定运控/MIT 使用 11 位标准帧和 8 字节 payload：接收帧标识符 = 电机 ID（默认 1），反馈帧标识符 = `0x00 + 驱动器 ID`。进入控制以末尾 `0xFC`（第 41 页原文加粗警告"使用 CAN 通信控制电机时必须先进入电机控制模式！"），退出以 `0xFD`，设置零位以 `0xFE`；普通命令按 position[16] / velocity[12] / Kp[12] / Kd[12] / torque[12] 位打包，反馈包含驱动器 ID、位置[16]、速度[12]、扭矩[12]、温度（`T_int-40`）和错误标志（该字节的故障码表手册**未给出**）。该 profile 不能因为"看起来像 MIT"而复用第三方旧 codec，必须按 L02 的范围、位域和标准帧 ID 单独实现。

**⚠ 归一化常量陷阱（2026-08-23 深读发现，安全相关）**：第 43 页示例代码用固定常量做位打包归一化——`P ±12.5 rad`、`V ±30 rad/s`、`T ±18 N·m`、`Kp 0~500`、`Kd 0~5`——而第 42 页"参数范围"表按型号给出的物理极限差异巨大（如 AK10-9 扭矩 ±65 N·m、AK80-64 ±144 N·m），示例代码并不按型号切换常量。**且第 42 页型号表（10 个型号）不含 AKE60-8**。定制实机固件在 MIT 编解码时实际使用哪套 MIN/MAX 常量必须先确认（[05 §5.1](05_decisions_and_open_questions.md) 问题 2/3），否则扭矩编码会产生系统性错误；MIT codec 的归一化常量必须来自逐台设备配置，禁止硬编码手册示例值。

L02 第 4 页注意事项第 4 条明确警告（2026-08-23 人工复核原文）："多种可选控制方式在驱动板运行时不可切换，且不同控制方式之间通信协议不同。如需切换，请重新启动电源，然后再进行更改。使用错误的协议控制可能会使驱动板烧毁！" 因此"支持两种"表示配置层可选择两种独立 profile，不表示 ACTIVE 时自动探测、混发或热切换；切换只能在停用、断能/neutral、重新 configure 并通过相应证据闸门后发生——且按手册要求需要重新上电。

#### 4.4.3 失控保护与固件升级（2026-08-23 新增）

- **失控保护**：第 18 页"应用功能"页面（原文："该页面主要为 CAN ID 设置、CAN 通讯速率以及 CAN 通讯突然中断的设置"）提供 `失控时间(ms)` 与 `失控刹车电流(A)` 两个参数——即命令中断看门狗机制**存在**，超时后以设定电流刹车。截图中两字段均为 0（疑似默认不启用）；出厂默认值、启用状态、取值范围与能否经 CAN 报文配置手册均未说明。协议正文没有对应的 CAN 设置报文，工程上大概率只能用 CubeMarsTool 逐台预配置。该参数属于 G0 必读项与 G3 前必配项。
- **固件升级**：第 25~26 页说明升级流程；红字警告"如果您的固件包含了伺服和 MIT 两种固件，请分别上传这两个固件，以确保两种模式的正常使用"——G0 固件取证时必须同时记录两个 .bin 的版本。
- **CAN ID/波特率修改**：仅见上位机界面路径（第 18 页），协议未定义修改 ID/波特率的 CAN 报文。

### 4.5 HighTorque USB CDC transport 参考边界

`hightorque_fdcan` 更像通信板的 transport 示例，而不是电机 SDK。源码观察到：

- `MODE_FDCAN_PASS (0x12)`；USB CDC 外层帧头、CRC8/CRC16 和批量 payload；
- 每条原始帧带 CAN ID、标准/扩展标志、Classic CAN/CAN-FD、BRS、长度和最多 64 字节数据；
- 默认扫描 `/dev/ttyACM*`、USB VID/PID `0xCAF1:0xFFFF`、串口 4,000,000 baud，并要求通信板版本至少 `4.8.8`；
- 示例没有完整 nominal/data bitrate 配置、硬件时间戳或错误帧 API；构造函数立即打开串口、查询版本，失败时 `exit(1)`。

因此项目只提炼一个可注入、可失败、由 `BusRuntime` 拥有的 `HighTorqueUsbCdcTransport`；它与 `FakeTransport`、SocketCAN transport 共享 `RawCanFrame` 契约，不能把 CDC framing、串口线程或厂家 motor class 直接塞入 codec/SystemInterface。

### 4.6 AK3.0 V3.2 补充 profile（非当前默认）

AK V3.2 使用 29 位扩展帧，扩展 ID 的低 8 位是 Drive ID，高位是功能/控制模式 ID。

| profile | 扩展 ID / 功能 ID | payload | 建议实现名 |
|---|---|---|---|
| servo 电流 | 功能 ID `1` | `int32(Iq[A] * 1000)`，4 字节 | `CubemarsAkV3ServoCodec` |
| servo 速度 | 功能 ID `3` | 电气转速命令，4 字节 | 同上 |
| servo 位置 | 功能 ID `4` | 位置命令，4 字节 | 同上 |
| servo 位置速度 | 功能 ID `6` | 位置、速度、加速度，8 字节 | 同上 |
| servo 失能 | 功能 ID `15` | 无 payload | 同上 |
| 反馈设置 | 功能 ID `16` | 2 字节设置；写入 Flash | 配置工具，不进入周期路径 |
| 力控/MIT-like | 控制模式 ID `8` | `Kp[12], Kd[12], position[16], velocity[12], torque[12]` | `CubemarsAkV3ForceCodec` |

**关键冲突**：旧 Arduino demo 的标准帧 MIT payload 顺序是 `position[16], velocity[12], Kp[12], Kd[12], torque[12]`。它与 V3.2 的帧类型和位序都不同。两者必须是不同的 codec，禁止用运行时猜测或一个布尔开关共用打包函数。

**资料事实与实现边界**：V3.2 手册称 AK3.0 的 servo 与力控模式“使用无需进行切换”。这说明同一匹配固件可能接受两个命令族，但不代表两台定制实机已经验证，也不代表控制器可在 ACTIVE 期间混发。当前架构仍在 `on_configure` 固定控制 profile 和可 claim 的命令接口。

### 4.7 AK3.0 补充状态反馈

| 报文 | 资料定义 | 软件处理 |
|---|---|---|
| `0x29` | 扩展帧，8 字节，周期上传可配置 `1–2000 Hz` | 作为基础状态帧；保存源到达时间和 age |
| `0x29` 字段 | 位置 `int16`（0.1°）、ERPM `int16`（10 ERPM）、Iq `int16`（0.01 A）、驱动板温度 `int8`、故障码 `uint8` | codec 保留原始值，再按已确认极对数/减速比映射 SI |
| `0x2A` | 可选额外位置扩展帧，前 4 字节为 `int32` 位置（0.01°） | 只有确有分辨率需求且预算通过才启用 |

反馈设置命令会写 Flash，不能在启动或周期循环中反复发送。`1–2000 Hz` 是协议可配置范围，不等于 2000 Hz 控制闭环已经在当前 Jetson、当前总线和两台实机上通过时序测试。

### 4.8 标准 AKE60-8 力矩候选参数

AK V3.2 第 37 页给出的标准 AKE60-8 参数为：

| 参数 | 标准资料值 |
|---|---:|
| 位置范围 | `-12.56 .. 12.56 rad` |
| 速度范围 | `-40 .. 40 rad/s` |
| 扭矩范围 | `-15 .. 15 N*m` |
| 扭矩系数 | `0.7382 N*m/A` |

手册明确给出 `T = Kt * Iq`，并把 `T` 定义为“输出端输出扭矩”。这使标准 `joint/effort` 映射从“完全未知”收敛为“有标准机型候选”。但定制结构和双编码器版本是否保持同一 Kt、减速比、方向及固件参数仍须通过供应商确认或每台实机 `.McParams`/`.AppParams` 证据锁定，不能先硬编码 `0.7382`。

## 5. 对 500 Hz 与 1 kHz 的影响

以下沿用经典 CAN 最坏位填充预算：8 字节扩展帧按 160 bit，4 字节扩展帧按 120 bit，位速率假设为 1 Mbit/s。HI12 仍按每台 3 个 8 字节扩展帧、100 Hz 估算。

| 场景 | 最坏流量 | 总线占用 | 结论 |
|---|---:|---:|---|
| 2 电机，8B 命令 + `0x29`，500 Hz | 320 kbit/s | 32.0% | 电机协议预算充足 |
| 上述电机 + 2 HI12 @100 Hz | 416 kbit/s | 41.6% | 当前 500 Hz 单物理通道静态预算候选；backend/时序仍待证 |
| 补充 AK3.0 假设：2 电机 8B 命令 + `0x29` + `0x2A` @500 Hz，再加 2 HI12 | 536 kbit/s | 53.6% | 非当前 L02 profile；若另证 AK3.0，仍超过 50% 平均目标 |
| 补充 AK3.0 假设：2 电机 8B 命令 + `0x29` @1 kHz，再加 2 HI12 | 736 kbit/s | 73.6% | 非当前 L02 profile；不适合作为单总线默认值 |
| 补充 AK3.0 假设：上一场景再启用 `0x2A` | 976 kbit/s | 97.6% | 非当前 L02 profile；拒绝该单总线配置 |

**规划目标（受 [ADR-006](../adr/ADR-006-conditional-can0-deployment.md) Proposed 约束）**：L02 伺服资料上限为 500 Hz，因此当前电机命令/反馈目标最高按 500 Hz 规划；这同时满足静态预算，但不证明当前单总线拓扑或 USB transport 时序已可激活。`controller_manager` 可独立支持 1 kHz 主机实验，不能据此把 L02 电机 I/O 升至 1 kHz。只有实机被证明采用相应 AK3.0 profile 时，才另行评估 1–2000 Hz 和 `0x2A`。

## 7. 对框架实现的约束

1. `mech_protocol_cubemars` 至少区分 `AK V1.0.18 servo-extended`、`AK V1.0.18 motion-control/MIT-standard` 两个当前 profile；AK V3 servo/force-control 可作为经过证据标记的补充 profile，不得与 L02 codec 共用有歧义的打包函数。
2. `DeviceSession` 绑定明确的协议代际、固件范围、Drive ID、反馈集合和编码器来源；ACTIVE 期间不自动识别或混发命令族。
3. `SystemInterface` 只暴露经 capability 证明的标准接口。若实际 CAN 位置来源未确认，`joint/position` 不得假定使用外编码器。
4. Kt、范围、极对数、减速比、方向、反馈率**以及 MIT 位打包归一化 MIN/MAX 常量**来自每台设备配置，不在 codec 中按型号硬编码（§4.4.2 陷阱：手册示例常量与型号物理极限不一致，且型号表不含 AKE60-8）。
5. `0x2A` 只在实机被证明采用相应 AK3.0 profile 时才可显式配置并进入总线预算；任何反馈设置/Flash 写操作都不进入普通启动或控制循环。
6. 现有 C++ 控制器仍只依赖 `position`、`velocity`、`effort` 和质量/新鲜度契约。未来更换其他 CAN 电机时，只要新 adapter 提供相同接口语义，控制器无需修改。

所有实机记录无无效 TX、无 USB 短写或失败，trace 未溢出，原始反馈故障码为 0。发送间隔超过 3/4/6 ms 的次数均为 0。这是间隔统计，不等于已经测量绝对 release deadline、完整丢包率或设备执行。双机每路平均约 500 Hz；新目标由 Python 约 47 Hz 更新，500 Hz 是底层重复刷新发送频率。

双机有效发送窗口内：104 反馈间隔 P99 20.049738 ms、最大 20.114637 ms；105 P99 20.071371 ms、最大 20.216687 ms。退出阶段曾有 164 ms 接收间隔，已与有效发送窗口区分。设备没有采样时间戳，不能从主机间隔推导内部采样/执行延迟。

105 本轮最高反馈 70 ERPM，未复现前一轮 130 ERPM 保护退出；不代表原异常根因已解决。104 双机窗口 ERPM 为 0。原始位置只有 0.1° 分辨率，本轮没有独立位移或力矩测量。两台最终均收到 0x77 失能 ACK；无遗留控制进程或串口占用。ACK 不代表机械制动。

## 软件基准与失败记录

- 真实 ROS controller_manager、EffortCommandController、Ak30System、MIT 编码及 USB transport，连接本次创建的私有 PTY；使用真实 steady clock，未接物理端口。模拟器为 Python，同进程中的接收线程会受到调度/GIL/垃圾回收影响。
- 30 s 详细记录：每路 15,006 帧，原生发送 P99 104=2.043123 ms、105=2.055508 ms；最大约 2.28 ms。PTY 接收端最大间隔约 35–37 ms，不能替代原生发送时间。
- 120 s 默认轻量记录：约 32.16 s 退出，两台控制器日志报告 update error，原始失败证据保留。接收端曾有约 93 ms 间隔；该次未启用原生 telemetry/trace，不能确定第一触发原因。
- 120 s 对照：在测试进程禁用自动 GC 并恢复原生 telemetry 后完成，两路各 60,005 帧，平均约 500 Hz。它是有明确条件的连续运行结果，不是默认配置通过；同时变更了 telemetry，且失败轮没有 GC 时间记录，不能断言 GC 是唯一根因或给出严格记录开销差值。
- 轻量模式关闭原生逐帧 trace，因此复用硬件检查器的 summary.json 保留 INCOMPLETE（缺少该类证据）；软件基准结果以 benchmark.json 的 complete 为准。120 s 不具备原生逐帧发送时间，PTY 接收最大 10.55/12.03 ms 不能视作控制线程延迟。

## 指标定义与边界

原生发送间隔：连续 transport_result 的 steady-clock 时间差。传输调用耗时：对应 transport_send 至 transport_result，包含主机封装、USB write 提交及记录开销；不包含 CAN 仲裁和设备执行确认。2 ms 是发送周期，不是整链路延迟。本轮没有目标关联序号及 ROS 发布/控制器接收计时点，未完成端到端时延、硬实时或 MuJoCo 闭环验收。

# MIT 主机端到端时延实测

日期：2026-11-06，Asia/Shanghai。用途：独立控制架构性能测试；Kp=Kd=0，名义力矩=0。用户已确认电机上电、机构独立支撑且无人穿戴。本轮未改阈值、固件、零位或持久参数。

## 结论与测量边界

完成 Windows 验证、Orin 原生构建/测试、5 s 私有 PTY 联测、105 单电机 5 s 和双电机 20 s 实测。下行链路采用目标序号关联：ROS 发布前 → 控制器回调 → 控制器更新完成 → 原生 USB transport 成功返回。双机每路 972/972 个目标匹配成功，主机下行 P99 为 3.60/3.73 ms，最大 4.35 ms。

这是主机可观测的端到端链路。USB 端点是主机完整写入提交成功返回，未测到 USB-CAN 板内排队、CAN 仲裁、电机接收和执行完成。电机反馈不回显目标序号或设备执行时间；不能把“下发后第一帧反馈”当作该命令响应，也不能把独立的下行和回传统计相加称为 RTT。全零指令只提供通信关联，不能提供机械响应时延。本轮不包含 IMU、MuJoCo 计算或上层反馈闭环决策。

## 实机下行结果

单位 ms，分位数为排序后 nearest-rank。窗口按 zero_effort_window_start/end 取实际发布时刻；原始启动/退出记录全部保留。控制线程 500 Hz，新目标约 48.6 Hz，二者分开统计。

| 运行 | 电机 | 匹配/发布 | P50 | P95 | P99 | 最大 |
|---|---:|---:|---:|---:|---:|---:|
| 单机 5 s | 105 | 244/244 | 3.279284 | 3.543898 | 4.251308 | 4.481778 |
| 双机 20 s | 104 | 972/972 | 3.208338 | 3.525178 | 3.604796 | 4.343470 |
| 双机 20 s | 105 | 972/972 | 3.097007 | 3.400214 | 3.729951 | 4.345390 |

双机各段：

| 段 | 104 P50 / P99 / 最大（ms） | 105 P50 / P99 / 最大（ms） |
|---|---|---|
| 发布前→控制器回调 | 0.347145 / 0.531022 / 0.918712 | 0.324776 / 0.542926 / 0.794964 |
| 回调→更新完成 | 0.934456 / 1.337474 / 1.954034 | 0.825461 / 1.363138 / 2.000499 |
| 更新完成→USB 提交返回 | 1.941233 / 2.013459 / 2.232217 | 1.955378 / 2.044084 / 2.270298 |

更新至写出约 2 ms 的原因由代码和记录共同支持：Ak30ForceControlRuntime 在 write 中保存 pending 命令，下一次 read 才提交。在 500 Hz 下引入约一个周期等待。本轮只测量，不改该调度契约。各段分位数不能直接相加得到总时延分位数。

双机各记录 10,005 次成功 MIT 发送（含结束交接阶段），TX 间隔 P99 104=2.048980 ms、105=2.068565 ms，最大 2.281626/2.301723 ms。有效窗口内无大于 3 ms 的 TX 间隔；无 USB 短写/失败、无无效 TX/RX、无 trace 溢出。全部 MIT 目标载荷为 0000007fff7ff7ff。零值编码存在 -15/4095 N·m 的协议量化偏差，它不是实测力矩。

## 反馈回传与长尾

回传定义：驱动给反馈帧标注的主机接收时刻 → ROS DynamicJointState 订阅回调。每个原始反馈序号只计第一次观察；双机窗口每路 1,000 个样本，主机序号无间断。该序号不能证明设备端绝对无丢帧。

| 双机阶段 | 电机 | 样本 | P50 / P95 / P99 / 最大（ms） |
|---|---:|---:|---|
| 完整 20 s 窗口 | 104 | 1000 | 0.864342 / 1.264448 / 9.827546 / 99.786477 |
| 完整 20 s 窗口 | 105 | 1000 | 0.829365 / 1.211807 / 10.995128 / 100.904457 |
| 第 1 秒之后，补充统计 | 104 | 950 | 0.864214 / 1.226943 / 1.516582 / 33.266191 |
| 第 1 秒之后，补充统计 | 105 | 950 | 0.829365 / 1.189471 / 1.615881 / 34.370251 |

1 秒分段用于描述启动过程，不替代全程结果。启动时测试节点已订阅，随后同步等待 controller spawner，订阅回调暂不执行；深度 100 的队列在进入窗口后继续消化，最早窗口样本回传约 100 ms。私有 PTY 也出现同类排队，最大约 165.5 ms；单机实测最大 97.9 ms。该实现和时序支持启动观察队列解释，未将其删除或计为稳态低延迟。

双机约第 7.6 秒还出现一次独立停顿：
- 105 新目标第 371 次发布间隔 54.022719 ms；同期 JointState 回调间隔约 39.21 ms。
- 两路 seq=600～602 回传各有三个 >5 ms 样本，最大 33.27/34.37 ms，随后恢复。
- 同期原生发送仍约 2 ms；全窗口反馈原生间隔最大 104=20.158850 ms、105=20.073311 ms。主机读取完成耗时全程最大仅 0.048481/0.046274 ms。
- 因此可定位到测试发布/观察层的暂停及积压；本轮没有 GC 或调度事件记录，不能断言具体根因。下行统计从实际 publish 起算，不包含本次“本该发布但尚未发布”的等待。

保留这一异常后，不能宣称完整 ROS 应用具备无长尾或硬实时保证。下一步若继续优化测试工具，应先将高频观察回调与测试编排隔离，并记录 GC/调度事件；保持保护参数不变后做相同条件对照。本轮未因此追加硬件试验。

## 关联方法与代码范围

测试入口为 tools/project/mit_latency.py；--simulate 使用本次创建的私有 PTY，--execute 才访问物理端口，--analyze 仅分析已结束目录。新输出必须位于 .local/validation，运行不自动重试。

- 目标携带随机运行 nonce、单调递增序号和主机 monotonic 发布时间；测试控制器只接受该身份，输出硬编码为零。
- 继承实际 SingleJointCommandController 的更新/命令代次逻辑，用 command_generation 关联实际 transport_result；不因载荷相同而猜配。控制器记录预分配，退出后落盘。
- 继承 Ak30System 增加测试时间戳状态接口，复用实际驱动、编码和传输；原始硬件 trace 同时检查 ID、零目标、写入成功、容量和时序。
- 新增 test/mit_timing_plugins.cpp、mit_timing_hardware.xml、mit_timing_controller.xml；仅 BUILD_TESTING 注册。
- ak30_system.hpp 放开派生并增加两个 protected 访问接口；CMakeLists.txt 增加测试插件。未替换正常控制插件、修改增益或改变生产调度。
- mit_communication.py 的计时功能为可选参数；新增 test_mit_latency.py。benchmark_mit_pty.py 仅减少终端 GC 明细输出，完整明细仍保存 JSON。

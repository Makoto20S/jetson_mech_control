# PH-EXO 并联外骨骼控制系统 · 文件架构与 Git 管理要求

版本：v1.4。更新日期：2026-11-10，Asia/Shanghai。
依据：用户确认统一控制工程、按需整体提交PR，并明确不纳入CAD/MATLAB项目、避免架构冗杂。
本文件是本项目文件组织与Git管理的统一要求；日后变更在此维护，不另建相互矛盾的要求副本。

## 1. 项目目标与范围

工程名称为 PH-EXO（并联外骨骼控制系统）。ROS 节点、话题等标识使用 ph_exo，当前状态节点为 ph_exo_state，话题为 /ph_exo/state。模型编号 REF-01 可追溯至 2026-10-24《REF-01 运动学理论推导》，其源码与数据文件沿用 ref01。jetson_mech_control 是 Git 仓库名，parallel_exo 是既有配置、文档和部署路径中的目录标识。

将ROS框架、电机相关实现、CtrBoard IMU、REF01运动学/动力学接口、运行必需的MuJoCo模型、配置、依赖和验证输入作为一个控制工程管理。通过Git迁移完整源码版本，在另一台符合环境要求的设备恢复开发、构建与运行条件。

工程组织以控制开发和设备迁移为目的，不默认拆成面向上游的独立贡献项目。需要时可以将本工程的阶段性成果整体形成一个PR。文件整合与控制功能实现分别验收。

## 2. 唯一正式源码入口

- 当前Windows入口：`C:/Users/admin/Desktop/SSH-ORIN/ROS工程/jetson_mech_control`。
- 当前开发分支：`ph-exo/development`。

- Windows/Linux按目标平台继续分工；Linux聊天的辅助文件、迁移日志和临时产物仍可存放于`Mujoco-Linux`。多个聊天不同时切换同一工作树的分支或覆盖同一文件。

## 3. 文件架构

```text
jetson_mech_control/
├─ ros2_ws/src/              ROS框架、电机、IMU等包；同名包只有一份正式源码
├─ mujoco/ref01/             控制计算所需的模型、参数、接口与计算依赖
│  ├─ config/                MJCF、运行必需的STL网格及模型参数
│  ├─ fixtures/              必要的小型冻结数值验证输入
│  ├─ tools/                 接口示例及必要验证工具
│  └─ docs/                  接口、单位和坐标说明
├─ config/parallel_exo/      本项目机器人配置基线与模板
├─ tools/project/            环境恢复、构建、验证和显式启动入口
├─ manifests/                固定依赖、构建组合与来源清单
├─ docs/parallel_exo/        本要求、恢复步骤和验证记录
└─ .local/                   本机环境、编译结果和缓存；不入Git
```

现有通用框架的其他目录继续按其职责使用，不为本项目复制另一套框架或重复包。新增目录、模块或抽象层必须对应实际控制或迁移需求；已有入口能够完成的工作优先在原入口完善。

## 4. 纳入与排除

| 纳入统一控制仓库 | 不纳入本控制工程 |
| --- | --- |
| 控制源码、IMU驱动及ROS接口 | CAD装配/零件源工程、MATLAB工程 |
| MuJoCo运行所需MJCF、STL与参数 | CAD提取、模型制作、Viewer及历史打包工具 |
| 运动学和动力学调用接口 | 与控制运行无关的历史报告和重复交接包 |
| 有来源记录的机器人配置、模板与依赖版本 | 虚拟环境、已安装依赖、构建结果、缓存 |
| 必要的小型测试基线与软件验证说明 | 长时间原始采集数据、安装日志及临时文件 |
| 恢复和构建所需脚本 | 账号凭据、私钥、令牌和本机私密配置 |

STL是运行资产，不能因为源自CAD就一并排除。冻结数值基线可以保留，但验证不得要求安装MATLAB。模型重新制作在独立建模项目完成，仅把明确版本的运行结果交付到控制仓库。原项目文件保留，不因本要求删除。

## 5. 包、IMU与配置管理

- 暂不用的已有包优先不启动，并按构建组合选择目标及其依赖；不要仅凭现场不用某个品牌就删除其依赖包。
- 当前构建组合为`imu`、`servo_imu`、`all`；构建与硬件启动分开。`mech_bringup`目前显式依赖达妙协议，因此该依赖不能随意跳过。
- 第五路CtrBoard配置及本项目串口适配集中在唯一的`mech_ctrboard_bridge`；`mech_protocol_ctrboard`负责协议。后续修改在这些正式包中继续，不在旧addon再维护第二套。
- `servo_pair.ref01.json`是现有机器人的配置基线，保留来源与适用硬件；`servo_pair.example.json`是结构示例。设备确认后的本机配置可放在忽略的`servo_pair.local.json`。
- 稳定设备标识优先于依赖主机插口位置的路径；换通信板或机器人时核对身份、映射和标定，不把旧设备参数视为通用默认值。
- 可执行入口按仓库位置解析源码和输出，不依赖旧Windows绝对路径、共享SSH目录或旧Orin release。历史证据允许保留原路径并注明用途。

保存文件、形成Git提交、推送远端、创建PR是不同操作。未提交或未推送的文件不会出现在另一台设备的远端clone中；已推送开发分支可直接拉取，无需等待PR合并。

按需交付流程：检查完整差异和文件范围 → 完成与改动相关的验证 → 整理提交并推送自己的远端 → 核对提交号 → 按用户要求整体发起PR。整体交付不要求把全部历史压成一个提交，也不包含未纳入范围的CAD/MATLAB资料和缓存。

需要接收上游版本时，先比较差异，在独立分支或副本合并与验证，通过后再整合进本项目。不得以“同步”为由强制覆盖用户修改、重置开发成果或自动更新已部署版本。

## 7. 本地编辑、SSH同步与设备迁移

日常开发以Windows本地统一仓库为唯一源码入口，Orin开发副本固定为
`/home/nvidia/parallel_exo_ros_framework/dev/jetson_mech_control`。
本地保存后先通过Windows状态逻辑与源码校验，再用`tools/project/Sync-Orin.ps1 sync`同步当前工作树，在该Orin目录构建和测试。sync入口自动执行本地状态校验，失败时不传输；
不要求先提交Git，也不自动推送或创建PR。`status`核对两端清单与哈希。

两端同步源码、模型、配置、依赖、运行说明及复现所需的冻结测试输入。原始采集、运行结果和验证报告归档在 Windows。报告放在 `reports/` 或 `docs/parallel_exo/reports/`，已有报告由同步排除名单管理。运行说明只记录规格和操作方法。每次测试结束后，按[测试结果归档](local_orin.md#测试结果归档)逐文件核验并清理 Orin 上对应的临时结果。机器配置和构建环境由各端维护。
远端源码不作为第二开发入口；发现独立改动先核对回本地，不强制覆盖。
同步只清理上次受管清单内且未产生独立修改的文件，不处理未知远端文件或现有发布目录。
同步与构建/测试互斥，构建记录绑定实际源码清单；操作说明见[本地与Orin同步](local_orin.md)。

通过Git迁往其他设备时仍执行以下流程：

1. 在原设备提交并推送所需完整版本，记录完整提交号。
2. 新设备clone或获取该分支，核对提交号一致。
3. 按锁定依赖重建本机环境；不复制另一系统的虚拟环境或安装目录。
4. 使用恢复入口验证模型/API，再在Linux目标设备构建和测试需要的ROS组合。
5. 核对机器人身份与现场配置；真实设备启动另行执行，不能作为clone、恢复或构建的隐含步骤。

源码完整性、独立路径恢复、软件测试、硬件采集与闭环控制验收分别记录。要求文件更新不触发重复硬件测试。

Git操作不自动改变Orin的`current`、`servo-current`或运行进程；部署需要明确目标版本、验证范围与回退方式。

具体恢复命令见[新设备恢复说明](restore.md)。

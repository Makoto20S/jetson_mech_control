你现在是本项目的首席系统架构师、机器人控制软件专家、ROS 2/ros2_control 专家、实时系统工程师和技术调研负责人。

本轮任务是**调研、论证并规划一套可长期扩展的通用机电控制系统框架**。不要立即编写真实设备驱动，不要开始堆砌 ROS 包，也不要把未经核实的协议假设写成事实。

## 一、项目根本目标

本项目虽然首先用于下肢外骨骼，但框架本身不应与某一种外骨骼机械结构绑定。它要解决的是一类通用问题：

- 在 NVIDIA Jetson 系列工控机上接入不同型号的电机、IMU 和 STM32 传感器节点；
- 通过 CAN/CAN FD 获取设备状态并发送位置、速度、力矩等命令；
- 为上层控制器提供稳定、统一、可测试的物理量接口；
- 让 PID、阻抗、滑模等 C++ 控制器可以作为 ros2_control 控制器加载、运行和切换；
- 让 Python 负责神经网络、深度学习、训练、推理和较低频策略，不进入确定性实时闭环；
- 更换 Jetson、电机、IMU 或增加 STM32 时，尽量不修改上层控制算法和实验流程；
- 通过 Git、文档、测试、配置和 AI 协作规范，使项目能够由多人长期维护。

当前 Jetson 只是验证机。未来仍以 NVIDIA Jetson 系列为主，但不能把代码硬编码到当前机器、当前 JetPack、当前 CAN 接口数量或当前目录结构。

## 二、一个月 MVP

计划在一个月内完成最初版本。MVP 必须达到：

1. Jetson 通过 CAN 稳定读取两台 HI12 IMU 的信息；
2. Jetson 通过 CAN 控制一台 CubeMars AKE60 系列电机；
3. 能读取电机位置、速度、电流/力矩、温度和故障等实际可用反馈；
4. 能让电机在受控台架条件下输出受限的恒定力矩；
5. 建立 ros2_control 硬件接入骨架；
6. 能加载并运行一个最简单的 C++ ros2_control 控制器；
7. 证明控制器能够通过 controller_manager 按生命周期规则加载、激活、停用和切换；
8. 具备基本诊断、超时、指令限幅、数据记录和可复现实验能力。

本轮只规划 MVP，不控制真实电机，不修改硬件配置。

## 三、设计规模

以以下规模作为当前设计包络，不需要为无限规模过度设计：

- 最多 6 台电机；
- 最多 2 条 CAN 总线；
- 2 台外部 HI12 IMU；
- 1 个 STM32 节点；
- STM32 未来采集足底压力和扭矩传感器，并将数据通过 CAN 发送给 Jetson；
- STM32 固件纳入同一个私有 Git 仓库，但首期只规划目录、接口、协议和测试边界，不开发实际固件。

## 四、已确认的软件边界

1. ros2_control 是首选核心方案，但不是未经论证的结论。请比较至少以下两种架构：
   - 以 ros2_control 为中心，设备驱动、硬件接口和 C++ 控制器均按其模型组织；
   - 独立的纯 C++ 传输/协议/实时核心，加 ros2_control 适配层。
2. 论证后给出明确推荐，不要只罗列优缺点。
3. 电机的 FOC、电流环、速度环和位置环由驱动板完成；Jetson 负责关节级外环、状态估计、控制器调度和高级算法。
4. C++ 负责确定性实时部分：SocketCAN、协议编解码、硬件接口、状态缓存、诊断关键路径、PID/阻抗/滑模等控制器。
5. Python 负责神经网络、深度学习、数据处理、训练、推理和较低频策略。Python 结果通过带时间戳、有效期和边界检查的实时缓冲交给 C++ 控制器。
6. MATLAB/Simulink 生成的算法属于后续扩展，可考虑生成 C/C++ 后包装成控制器插件，本阶段不实施。
7. 框架概念上支持 position、velocity、effort 三类命令接口，但具体设备只能暴露其当前固件和工作模式真正支持、且语义明确的接口。
8. 控制器应支持通过 controller_manager 切换。请设计接口所有权、切换前后状态、命令连续性和失败回滚方案。
9. 不预设控制循环必须为 500 Hz。请根据设备协议、反馈频率、CAN 带宽、Linux 调度抖动和控制需求进行论证，给出推荐频率、测量方法和验收指标。

## 五、硬件与协议事实

### 1. CubeMars 电机

- 当前只能确认属于 AKE60 系列，准确型号、减速比、驱动板硬件版本和固件仍需现场核实；
- 本地手册：`docs/ak-series-driver-manual-v1-0-18-for-ak-2-0-robotic-actuator-cn.pdf`；
- 手册显示驱动器具有伺服模式和运控/MIT 模式；
- 伺服模式使用 CAN 扩展帧，支持占空比、电流、电流刹车、速度、位置、位置—速度等命令，反馈周期可设置为 1～500 Hz；
- 运控/MIT 模式使用 CAN 标准帧，命令包含目标位置、速度、Kp、Kd 和前馈力矩；
- 伺服模式与运控模式协议不同，不能假设运行中无缝切换；
- 手册中的 AK60-6 等参数不能直接当作未知 AKE60 型号的参数；
- 在准确型号确认前，不得写死位置、速度、力矩范围、Kt、减速比或反馈语义；
- 电流命令不能未经标定就宣称等于准确的关节输出力矩。

### 2. HI12 IMU

- 本地资料：`docs/hi12_datasheet_cn.pdf` 与 `docs/imu_cum_cn.pdf`；
- 两台设备确认使用 CAN，但当前没有确认或配置为 CANopen；
- 手册说明标准交付通常默认为 J1939：CAN 2.0B 扩展帧、默认 500 kbit/s、默认节点地址 8；
- CANopen 是特定交付/定制固件能力，不能假设普通配置命令可以把 J1939 固件变成 CANopen；
- 实际型号、PNAME、APP_VER、固件能力和当前输出协议必须现场读取或抓包确认；
- 如果两台 IMU 都是默认节点 8，应逐台配置成不同节点；
- CubeMars 通常使用 1 Mbit/s，而 HI12 默认可能是 500 kbit/s，共总线前必须先逐台完成协议、波特率和节点配置；
- 真正的同步采样/触发主要依赖 SYNC_IN/PPS 等硬件同步能力；不要把 CANopen SYNC 或同时收到报文直接等同于严格同步采样；
- 不得仅根据标准帧/扩展帧标志区分电机和 IMU。J1939 IMU 与伺服模式电机可能同为扩展帧；CANopen IMU 与 MIT 模式电机可能同为标准帧。路由应基于总线、CAN ID/掩码、设备实例和已选择协议。

### 3. STM32

- 选用达妙 DM-MC-Board02，主控 STM32H723VGT6；
- 本地手册：`docs/stm32.pdf`；
- 开发板提供 3 路 CAN FD、SPI、I2C、串口和板载 BMI088；
- 板上只明确看到一路可复用 ADC 引脚，未来多通道足底压力或桥式扭矩传感器可能需要外接 ADC、放大、滤波或其他模拟前端；
- 传感器具体数量、信号形式和采样率尚未确定，不要在本阶段虚构 ADC 方案；
- 请只设计 STM32 节点在系统中的职责、消息语义、时间戳、序号、状态、标定和诊断边界。

## 九、软件与配置原则

- 设备传输和协议编解码优先写成可脱离 ROS 测试的纯 C++ 库；
- 未连接硬件时也能通过 vcan、回放报文和仿真设备运行测试；
- 原始协议参数、物理单位、坐标转换和错误码必须有单一可信定义；
- 设备 ID、总线、协议、波特率、方向、减速比、零位、限值和频率来自配置，不硬编码在控制器中；
- 不要把不同固件语义强行伪装成完全相同的接口；
- 不要让 Python、DDS、磁盘 I/O、网络等待或动态分配进入确定性控制更新路径；
- 软件层仍需规划命令超时、数据新鲜度、限幅、故障锁存和诊断接口，但本任务不负责机械与电气安全系统设计；
- 所有重要架构决定使用 ADR 记录；
- 文档、接口契约和测试是项目事实来源，AI skills 不能代替项目文档。

## 十四、一个月路线的最低验收要求

你提出的路线必须确保月底前可以客观验证：

- 项目可以在当前 Jetson 上可重复构建；
- vcan 和已知报文测试可验证协议框架；
- 两台 HI12 的准确型号、固件、协议、节点和波特率已识别；
- 能稳定接收并解析两台 IMU 所需数据；
- 一台 AKE60 的准确型号、驱动板版本、工作模式和反馈语义已识别；
- 能读取单电机反馈；
- 能在受限台架条件下发送受限恒定力矩命令；
- ros2_control 硬件组件可以配置、激活和停用；
- 至少一个简单 C++ 控制器可以加载运行；
- 至少演示一次受控的控制器切换；
- 通信异常和命令超时能够被检测并反映到诊断与硬件生命周期；
- 实验对应明确 Git commit/tag、配置和日志；
- 没有使用猜测的协议字段或未经核实的力矩参数。

## 十五、工作方式

1. 先阅读全部本地资料和现状，不要一上来输出通用 ROS 教程；
2. 再做广泛但有筛选标准的调研；
3. 对关键结论给出来源、证据和日期；
4. 遇到资料冲突时明确列出冲突，不要自行挑一个版本；
5. 优先复用成熟组件，但保留项目特有的薄适配层；
6. 不要只给一种方案，先比较后决策；
7. 不要为了显得完整而加入当前没有价值的微服务、云平台、数据库或复杂前端；
8. 对一个月无法完成的内容明确放入后续阶段；
9. 如果仍有问题，先完成所有只读调查，再只询问真正阻塞架构决策的少量问题；
10. 最终方案必须能指导团队下一步直接建立 Issue 和开始开发。

现在开始：先盘点本地材料与 Jetson，只读收集事实；然后调研现有工作；最后提交完整规划，不要进入实现阶段。
